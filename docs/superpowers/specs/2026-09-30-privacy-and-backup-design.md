# 개인정보 처리와 백업 설계

작성일: 2026-09-30
상태: 설계 합의됨 (구현 계획 대기)
선행 관계: 이 문서의 1·2번은 [공개 발행](2026-09-30-public-publishing-design.md)과
[모니터링](2026-09-30-monitoring-design.md)보다 **먼저** 끝나야 한다.

## 배경

지금까지는 사용자가 사실상 운영자 한 명이라 개인정보를 따질 일이 없었다. 그런데 공개 발행
기능으로 **남의 가입을 받기 시작하면** 의무가 생긴다. 또 모니터링 도구(Sentry·PostHog)는
해외 서버라 **국외 이전**이 발생하는데, 이를 고지할 문서가 지금 없다.

현재 상태를 점검한 결과는 이렇다.

**되어 있는 것**: 비밀번호 미저장(GitHub OAuth), DB 리전 서울, RLS로 계정 격리,
클라이언트에 publishable 키만, `on delete cascade`로 삭제 연쇄 준비됨.

**빠진 것**: 처리방침 없음, **회원 탈퇴 기능 없음**, 수집 항목 미고지, 보유기간 정책 없음,
**백업 없음**(Free 플랜은 자동 백업이 없다).

## 1. 회원 탈퇴

가장 시급하다. 지금은 로그아웃만 있고 **사용자가 자기 데이터를 지울 방법이 앱에 없다.**

브라우저에서는 계정을 삭제할 수 없다. `auth.admin.deleteUser`는 `service_role` 권한이
필요한데, 그 키는 절대 클라이언트에 둘 수 없다(RLS를 통째로 우회한다). 따라서:

- **Supabase Edge Function** `delete-account`를 만든다. 함수 안에서만 `service_role`을 쓰고,
  호출자의 JWT에서 사용자 id를 확인한 뒤 **그 사용자 자신만** 삭제한다.
- 계정이 지워지면 `maps`·`profiles`는 `on delete cascade`로 함께 사라진다.
- 앱에서는 계정 메뉴에 "회원 탈퇴"를 두고, 되돌릴 수 없음을 알리고 한 번 더 확인받는다.
- 탈퇴 후 브라우저의 IndexedDB 로컬 사본도 지운다. 서버만 지우면 그 기기에 남는다.

이것이 이 프로젝트의 **첫 서버 코드**가 된다. 나중에 Spring을 붙일 때의 예행연습이기도 하다.

## 2. 개인정보 처리방침

앱 안에 페이지 하나(`/privacy`)로 둔다. 담을 내용:

| 항목 | 내용 |
|---|---|
| 수집 항목 | 이메일·프로필(GitHub OAuth 제공), 작성한 맵과 노트, 접속 로그 |
| 수집 목적 | 로그인, 맵 저장·동기화, 오류 대응 |
| 보유 기간 | 탈퇴 즉시 파기. 삭제한 맵은 30일 뒤 완전 삭제 |
| 국외 이전 | Sentry·PostHog(해외). DB는 서울 리전 |
| 파기 절차 | 계정 메뉴의 회원 탈퇴 |
| 문의처 | 운영자 이메일 |

**모니터링 도구를 붙이기 전에** 이 페이지가 있어야 한다. 순서를 지키는 이유가 이것이다.

## 3. 보유 기간 (소프트 삭제 정리)

지금은 맵을 지워도 `deleted_at`만 찍히고 영원히 남는다. 이 방식 자체는 필요하다 — 실제로
지우면 다른 기기가 "여긴 없네" 하고 되살려 올리기 때문이다. 하지만 영구 보존은 처리방침과
맞지 않는다.

**`deleted_at`이 30일 지난 행을 완전히 지운다.** 30일이면 모든 기기가 삭제를 전파받고도
남는다. 실행 수단은 `pg_cron`(Supabase에서 사용 가능한지 확인 필요)을 우선하고, 안 되면
아래 백업 워크플로에 같이 얹는다.

## 4. 백업

Supabase Free 플랜은 **자동 백업이 없다.** 공식 문서도 "CLI로 직접 덤프해 외부에 보관하라"고
권고한다. 지금 프로젝트를 실수로 지우거나 DB가 깨지면 복구 수단이 없다.

**방식: 주 1회 GitHub Actions가 `pg_dump` → 별도 비공개 저장소에 커밋.**

- **이 저장소(`mind_map`)는 PUBLIC이다.** 공개 저장소의 Actions 아티팩트는 누구나
  내려받을 수 있으므로, 사용자 데이터를 아티팩트로 올리면 백업이 아니라 유출이다.
  반드시 **별도 private 저장소**에 넣는다.
- GitHub 러너는 IPv4만 되고 Supabase 직접 연결은 IPv6다. **Session Pooler 연결 문자열**을
  써야 한다. 여기서 막히는 경우가 흔하다.
- 비밀값: DB 접속 문자열, 백업 저장소 푸시용 토큰. 둘 다 Secrets에 둔다.
- 덤프에는 다른 사용자의 개인정보가 들어 있다. 이 보관 사실을 **처리방침에 적는다.**

**복원 리허설을 한 번 한다.** 복원해 보지 않은 백업은 백업이 아니다. 로컬 Postgres에 덤프를
넣어 맵이 살아나는지 확인하고, 그 절차를 이 문서에 추가한다.

사용자가 실제로 늘면 Supabase Pro($25/월, 일일 백업 7일 보관)로 올리는 것이 정답이다.
그때는 "백업 없음"이 방어되지 않는다.

## 구현 순서

1. 회원 탈퇴 (Edge Function + UI)
2. 개인정보 처리방침 페이지
3. 보유 기간 정리 (30일 후 완전 삭제)
4. 주간 백업 + 복원 리허설
5. → 이후 모니터링, 그다음 공개 발행

## 테스트

- Edge Function: 남의 id를 넣어 호출하면 거부되는지 (JWT의 id만 삭제 가능)
- 탈퇴 후 해당 사용자의 `maps`·`profiles`가 실제로 사라졌는지 SQL로 확인
- 로컬 IndexedDB가 비워지는지
- 백업: 덤프 파일이 비어 있지 않은지 워크플로가 검증하고, 실패 시 빨간불
