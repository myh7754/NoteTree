# 사용자별 공개 발행 설계

작성일: 2026-09-30
상태: 구현·배포 완료 (2026-10-01)

## 배경

지금 공개 기능은 `showcase_owners`에 등록된 **계정 하나**(운영자)만 비로그인 방문자에게
보여준다. 즉 "내 포트폴리오 전용"으로 박혀 있고, 다른 사용자가 자기 공부 기록을 공개할
길이 없다.

그런데 관찰된 수요는 그 반대였다. 공부한 내용을 감추고 싶어 할 거라 짐작했지만, 실제로는
**공개해서 그걸로 어필하려는 사람들**이 있다. 이 문서는 그 수요를 제품 구조에 반영한다.

## 목표

1. 누구나 자기 맵을 공개할 수 있다. 기본은 비공개이고, 공개는 본인이 켠다.
2. 공개한 사람은 자기 맵을 **한 페이지에 모아** 남에게 보여줄 수 있다 (포트폴리오 용도).
3. 운영자 포트폴리오도 특별 취급을 없애고 이 기능의 첫 사례가 된다.

## 비목표 (이번에 만들지 않는 것)

- 방문자가 공개 맵을 자기 계정으로 **복제**하는 기능
- 조회수·좋아요 등 반응 지표
- 공개 맵 둘러보기 갤러리 (사용자가 늘기 전까지는 빈 화면이 된다)
- 링크 미리보기(OG 태그)·검색엔진 최적화
- 발행/초안 분리 — 편집 내용은 공개본에 즉시 반영된다

## 데이터 모델

```sql
-- 새 테이블: 닉네임. 공개 주소 /u/<handle> 의 근거.
create table public.profiles (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  handle     text not null unique,
  created_at timestamptz not null default now()
);

-- 기존 maps 에 두 컬럼 추가
alter table public.maps add column is_public boolean not null default false;
alter table public.maps add column slug text unique;
```

`is_public`의 기본값이 `false`인 것이 이 설계에서 가장 중요한 한 줄이다. 남의 공부 기록이
의도치 않게 노출되는 것이 이 기능에서 일어날 수 있는 최악의 사고다.

### 슬러그 규칙

`제목-난수6자` 형식 (예: `자바의신-a1b2c3`). 난수를 붙이는 이유는 제목이 겹쳐도 충돌하지
않게 하기 위해서다. **한 번 만들면 고정한다** — 제목을 바꿔도 슬러그는 그대로 둔다. 안 그러면
남에게 보낸 링크가 조용히 깨진다.

### 닉네임 규칙

소문자·숫자·하이픈만 허용, 유일해야 한다. 처음 공개를 켤 때 닉네임이 없으면 입력받는다.

## 권한 (RLS)

익명 읽기 정책을 `showcase_owners` 기준에서 다음으로 바꾼다.

```sql
-- maps: 익명은 공개된 것만 읽는다
using (is_public = true and deleted_at is null)

-- profiles: 익명은 닉네임을 읽을 수 있다 (공개 페이지 주소 확인용)
using (true)
```

쓰기 정책(`본인 맵만 수정/삭제`)은 **그대로 둔다**. 읽기만 넓어지고 쓰기는 여전히 본인만이다.
`showcase_owners` 테이블은 삭제한다.

### 개인정보

공개 페이지에 이메일을 싣지 않는다. 노출되는 것은 닉네임과 맵 내용뿐이다. 이메일은
`auth.users`에 있고 클라이언트 키로 접근할 수 없다. 즉 공개 경로로 새어나갈 수 있는
개인정보는 **사용자가 직접 정한 닉네임**과 **본인이 공개로 켠 맵의 내용**으로 한정된다.

## 라우팅

```
/            비로그인 → 서비스 소개·사용법 (정적 페이지)
             로그인   → 편집 앱 (지금과 동일)
/u/<handle>  그 사람이 공개한 맵 목록
/m/<slug>    공개 맵 하나 (읽기전용 뷰어)
```

**라우터 라이브러리를 넣지 않는다.** 경로가 3개뿐이라 `pathname`을 파싱하는 순수 함수
(`src/utils/route.ts`) 하나로 충분하다.

`vercel.json`에 SPA rewrite가 **반드시** 필요하다. 없으면 `/m/...`에서 새로고침할 때 404다.
(예전 메모에 "라우터가 없어 vercel.json이 불필요"라고 적혀 있었으나, 이 설계부터는 필요하다.)

## 화면

| 화면 | 내용 |
|---|---|
| 소개 페이지 (`/`) | 서비스 설명·사용법, 로그인 버튼, 예시로 운영자 맵 링크 |
| 공개 목록 (`/u/<handle>`) | 카드: 제목, 노드 수, 최종 수정일 |
| 공개 뷰어 (`/m/<slug>`) | 기존 `ShowcaseViewer` 재사용 |
| 공개 토글 | 툴바에 공개 스위치 + 링크 복사 버튼 |
| 닉네임 입력 | 처음 공개를 켤 때만 뜨는 모달. 중복이면 거절 |

### 뷰어 초기 상태 (같이 고치는 것)

공개 뷰어는 **깊이 2까지만 펼친 상태**로 시작한다. 지금은 217노드가 전부 펼쳐진 채 화면에
맞춰져 글자가 안 읽힌다. 남에게 보여주는 것이 목적인 기능에서 이건 곧 첫인상이므로, 뷰어
코드를 건드리는 김에 함께 고친다.

## 기존 상태 이전

1. 운영자 계정의 `profiles`에 닉네임 한 줄 추가
2. 공개할 맵을 `is_public = true`로 켜고 슬러그 생성
3. `showcase_owners` 테이블과 관련 정책 삭제
4. `src/db/showcase.ts`를 `loadPublicMapsByHandle` / `loadPublicMapBySlug`로 교체

이력서에 이미 뿌린 `/` 링크는 소개 페이지로 바뀐다. 소개 페이지 상단에 운영자 맵으로 가는
버튼을 크게 두어 도달 경로를 유지한다.

## 테스트

- **순수 함수 유닛 테스트**: 경로 파싱(`/m/abc` → `{kind:'map', slug:'abc'}`), 슬러그 생성
  (한글·공백·제목 중복), 닉네임 검증
- **스토어 테스트**: 공개 토글이 `is_public`과 슬러그를 올바로 세팅하는지
- **RLS 검증 스크립트**: 익명 키로 ① 비공개 맵 조회 → 0행 ② 공개 맵 조회 → 1행
  ③ 익명 수정 시도 → 차단. 권한은 코드가 아니라 DB가 지키므로 실제 DB에 대고 확인한다.

## 나중에 올릴 수 있는 것

초안 보호가 필요해지면 발행 모델(공개용 스냅샷 + "발행" 버튼)로 올릴 수 있다. `is_public`
구조에서 컬럼을 추가하는 방향이라 막히지 않는다.


## 구현 기록 (2026-10-01)

- 경로 파싱은 **조각 수가 정확히 2개**일 때만 /u·/m로 받는다. `/u/a/b`를 "닉네임 a"로
  관대하게 받으면 오타 난 주소가 엉뚱한 사람의 공개 목록을 띄운다. 공개 기능에서
  관대한 파싱은 곧 정보 노출 경로다.
- 잘린 링크(`%E`로 끝나는 등)에 `decodeURIComponent`가 던져 앱이 통째로 하얘지는 걸
  막는다(`safeDecode`). 잘린 링크의 올바른 결말은 흰 화면이 아니라 홈이다.
- 슬러그는 **처음 공개를 켤 때 한 번만** 만든다. 끌 때도 지우지 않는다 — 다시 켜면
  같은 링크여야 한다. `src/db/publish.test.ts`가 이 네 경우를 고정한다.
- 공개를 켜기 전에 `syncNow()`를 먼저 돌린다. 맵은 평소 IndexedDB에만 있어서,
  동기화 없이 공개하면 방문자가 **서버에 마지막으로 올라간 옛 판본**을 본다.
- 뷰어 초기 깊이 2는 스토어에 이미 있던 `expandToLevel`을 불러 쓴다(새 코드 없음).
- "없는 닉네임"과 "공개한 맵 0개"를 다른 화면으로 구분한다. 뭉개면 주소를 잘못 친
  사람이 "이 사람은 아무것도 안 올렸네"로 오해한다.

### 배포 후 확인에서 잡은 것 두 가지

코드 리뷰와 테스트를 모두 통과했는데도 **실제 배포본을 열어보고서야** 드러난 문제다.

1. **고정 깊이 2가 목적을 달성하지 못했다.** 설계는 "깊이 2"라고 적었지만 의도는
   "글자가 읽히는 첫인상"이었다. 실제 데이터에서 자바는 깊이2가 62개라 여전히
   안 읽혔고, msa는 10개라 너무 적었다. 맵마다 모양이 달라 깊이를 고정하면 어떤
   맵에서는 반드시 틀린다 → 노드 수 예산(약 25개)으로 바꿨다.
2. **툴바가 공개 중인 맵을 "비공개"로 표시했다.** 공개 상태를 패널 열 때만 읽어
   쿼리를 아꼈는데, 읽기 전까지 기본값이 "비공개"였다. 개인정보 기능에서 가장
   나쁜 방향의 오류다 — 사용자를 안심시킨 채 노출시킨다.

### 실제 DB로 검증한 것 (scripts/verify-rls.mjs)

맵 하나를 실제로 껐다 켜며 확인했다. 끈 순간 익명 시야에서 9행 → 8행으로 사라졌고,
다시 켰을 때 슬러그(`msa-jeyngl`)가 그대로여서 링크가 유지됨을 확인했다.
익명의 수정·삭제·닉네임 선점은 모두 0행으로 막혔다.

### 아직 브라우저로 확인하지 못한 것

소개 페이지(`/`)는 **로그아웃 상태에서만** 보이므로, 사용자를 로그아웃시키지 않고는
실물 확인이 불가능했다. 라우팅 분기와 컴포넌트는 테스트로 덮여 있다.


## 2026-10-02 변경: 주소 형태와 전체 공개 모드

사용자 요청으로 두 가지를 바꿨다. 위 본문의 "슬러그 규칙"과 "라우팅"은 이 절로 대체된다.

### 주소: /m/<닉네임>/<슬러그>

- 슬러그는 제목 그대로다(난수 없음). 닉네임이 주소에 들어가므로 **그 사람 안에서만**
  유일하면 된다. 같은 사람이 같은 제목을 또 공개하면 `자바-2`, `자바-3`이 된다.
- DB의 유일 제약도 전체(`slug`)에서 사람별(`owner_id, slug`)로 바꿨다.
- 옛 주소(`/m/자바-0fdv4f`)는 `legacy_slug` 컬럼에 남겨 새 주소로 넘겨준다
  (`LegacyMapRedirect`). 이미 보낸 링크를 깨뜨리지 않기 위해서다.
- "한 번 만든 슬러그는 바꾸지 않는다"는 규칙은 그대로다.
- 닉네임을 바꾸면 그 사람의 모든 링크가 바뀐다. 지금은 닉네임 변경 기능이 없어 문제가
  없지만, 만들 때는 옛 닉네임도 넘겨줘야 한다.

### 전체 공개 모드 (profiles.auto_public)

- 설정창의 전체 토글은 "전부 공개인가"가 아니라 **모드**를 나타낸다. 켜 두면 새로 만드는
  맵도 공개된다.
- 새 맵 공개는 자동 저장이 서버에 올린 직후 앱이 한다(`maybeAutoPublish`). "새 맵"의
  기준은 슬러그가 한 번도 만들어진 적 없는 것 — 슬러그는 있는데 비공개인 맵은 사용자가
  직접 끈 것이므로 건드리지 않는다.
- 맵 하나를 개별로 끄면 모드도 꺼진다. 일부를 비공개로 돌린 사람에게 새 맵을 계속 자동
  공개하는 건 그 사람의 뜻과 어긋난다.
- 전체 공개를 켜다 중간에 실패하면 모드는 켜지 않는다.

ponytail: 새 맵 공개를 DB 트리거가 아니라 앱이 한다. 다른 기기·옛 버전 앱으로 만든 맵은
그 기기가 새 버전으로 저장할 때까지 공개되지 않는다. 그게 문제가 되면 insert 트리거로 옮긴다.
