# 모니터링·분석 설계

작성일: 2026-09-30
상태: 설계 합의됨 (구현 계획 대기)

## 배경

지금 이 서비스는 **아무 계기판이 없다.** 2026-09-24에 Supabase가 정지돼 사이트가 9일 가까이
죽어 있었는데, 사용자가 알려주기 전까지 아무도 몰랐다. 가입자 수도, 방문자 수도, 어떤 기능이
쓰이는지도 모른다.

## 목표

1. **살아 있는지** 안다 — 에러가 나면 알림이 온다.
2. **누가 오는지** 안다 — 방문자 수, 가입자 수, 재방문.
3. **어떻게 쓰는지** 안다 — 어떤 기능을 쓰고 어디서 막히는지.
4. 나중에 **Spring 서버를 붙여도** 같은 체계로 이어진다.

## 구조

이 앱은 서버가 없다(정적 SPA + Supabase BaaS). 그래서 텔레메트리는 **브라우저가 직접**
수집처로 보낸다(RUM). 서버가 없어 못 보는 DB·API 지표는 Supabase가 자체 제공한다.

| 역할 | 도구 | 비고 |
|---|---|---|
| 에러 추적 | **Sentry** | 프론트 표준. 소스맵 업로드로 스택트레이스 복원 |
| 방문자 수 | **Vercel Web Analytics** | 쿠키리스. Hobby 월 5만 이벤트, 커스텀 이벤트 불가 |
| 기능 사용 | **PostHog** | 무료 월 100만 이벤트. 서버 SDK(Java 포함)가 있어 Spring 확장에 유리 |
| DB·API·인증 로그 | **Supabase Studio Logs** | 이미 있다. 느린 쿼리·API 오류 |
| 가입자·맵 수 | **SQL 집계** | 새 도구 불필요 |

## 개인정보 (되돌리기 어려운 결정)

- **세션 리플레이는 끈다.** 마인드맵 화면에는 노트와 맵 내용이 그대로 보이므로, 녹화하면
  남의 공부 기록을 영상으로 보관하게 된다. 얻는 것보다 위험이 크다.
- **사용자 식별은 Supabase `user.id`(UUID)만 쓴다.** 이메일·이름을 분석 도구로 내보내지
  않는다. UUID만으로도 재방문·유지율은 다 보인다.
- **사용자 콘텐츠를 이벤트 속성에 넣지 않는다.** 노트 본문, 맵 제목, 노드 라벨은 금지.
  식별자(맵 id)와 수치(노드 개수)만 보낸다.
- 국내 개인정보보호법은 쿠키 동의를 필수로 요구하지 않지만, **개인정보 처리방침 페이지는
  만든다.** 이미 이메일과 맵 내용을 저장하고 있으므로 분석 도구와 무관하게 필요하다.

## 이벤트 설계

이름은 `영역_동작` 형식(snake_case). 처음에 넣을 것만 최소로 잡는다.

| 이벤트 | 언제 | 속성 |
|---|---|---|
| `map_created` | 맵 생성 | `map_id` |
| `node_added` | 노드 추가 | `map_id`, `depth` |
| `note_saved` | 노트 저장 | `map_id`, `length_bucket`(본문 아님, 길이 구간) |
| `search_used` | Ctrl+F 검색 | `result_count` |
| `map_published` | 공개 토글 켬 | `map_id` |
| `export_used` | 내보내기 | `format` |

공통 속성: 앱 버전, 로그인 여부. **자동 수집(autocapture)은 끈다** — 라벨 텍스트가 딸려
들어오는 경로를 막기 위해서다.

## Spring 서버를 나중에 붙일 때

지금 구조가 그때 발목을 잡지 않도록 두 가지를 지킨다.

1. **수집 호출을 한 파일에 가둔다** (`src/lib/analytics.ts`의 `track(event, props)`).
   화면 코드는 PostHog를 직접 부르지 않는다. 나중에 같은 이벤트를 Spring 수집 API로도
   보내거나 도구를 갈아탈 때 이 파일만 고치면 된다.
2. **식별자를 서버와 공유한다.** 프론트에서 쓰는 `user.id`(Supabase UUID)를 Spring에서도
   그대로 쓰면, 서버에서 보낸 이벤트와 브라우저 이벤트가 같은 사용자로 붙는다.

Spring이 생기면 그때 추가되는 것:

- **Sentry**: `sentry-java`로 서버 예외 수집. 프론트와 같은 프로젝트에 묶으면 요청 하나가
  브라우저→서버로 이어진 트레이스로 보인다.
- **PostHog Java SDK**: 서버에서만 아는 사건(결제, 배치 처리 결과)을 같은 이벤트 체계로.
- **APM·로그**: 서버가 생겨야 Pinpoint·ELK·Prometheus가 의미를 갖는다. 그건 그때 별도로
  설계한다. 지금 이 앱에 미리 만들 것은 없다.

## 알림

에러가 나도 모르고 지나가는 게 이번 장애의 본질이었다. Sentry에서 **새 이슈 발생 시 메일**
알림을 켠다. 이미 GitHub Actions의 Supabase keepalive 실패 알림이 있으므로, 둘을 합치면
"죽었는데 아무도 모름"은 막힌다.

## 범위 밖

- Grafana·OpenTelemetry 대시보드 — 이 앱에서 넣을 데이터가 프론트 지표뿐이라 얇다
- A/B 테스트·피처 플래그
- 세션 리플레이 (위 참고)

## 테스트·검증

- `track()`이 사용자 콘텐츠를 절대 싣지 않는지 유닛 테스트 (금지 키 검사)
- 개발 환경에서는 전송하지 않고 콘솔로만 출력 (실 데이터 오염 방지)
- 배포 후 Sentry에 의도적 에러 1건을 던져 알림이 오는지 확인
